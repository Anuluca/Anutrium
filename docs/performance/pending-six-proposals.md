# 六组待验证方案：收益、取舍与验证方法

## 前提

- 这些是进一步优化的候选方案，本次不直接实施。
- 本次已经落实首屏 UI 依赖、装饰暂停、矩阵去重、材质按变化同步、碑文绘制缓存、About 预取、页脚 transform 动画与字体缓存容量。
- 应先以新版本建立基线；此前的 CPU 热点被消除后，旧热点的相对收益可能改变。
- 比较时保持设备、浏览器、GPU 后端、视口、DPR、数据与动画时长一致；CPU 主线程耗时、GPU 时间和网络传输分别统计。不能用绘制调用减少比例代替 CPU 降幅。

## 1. 方尖碑/底座/倒影实例化、合并，以及零强度灯光

### 原理与可能收益

- 实例化 (Instancing) 让共享几何与材质、仅变换不同的多个对象用较少绘制调用提交。静态几何合并也能减少对象与提交数量。
- 当前同类碑体、底座和倒影存在重复几何。可能减少 WebGL 驱动提交、状态切换与场景对象处理；三角面总量不一定减少。
- 灯光强度为 0 不必然意味着 Three.js 不再准备该灯光数据。固定数量灯光仍可能进入渲染数据和着色器的灯光循环。
- [Three.js InstancedMesh 官方说明](https://threejs.org/docs/pages/InstancedMesh.html)确认适用条件是共享几何/材质、不同变换，并以减少 draw calls 为目的。

### 为什么仍需验证

- 每根方尖碑有不同的主题、悬停亮度、发光、渐隐、聚焦状态。`instanceColor` 只解决基础颜色，其他差异可能需要实例属性和自定义着色器。
- 透明晶体、倒影有绘制排序要求；合并后不能继续像独立 Mesh 一样自由排序。倒影的负缩放也要验证。
- 用户点击、Tab 聚焦、命中对象 ID、动态包围范围都要重新映射。
- 直接隐藏/移除强度为 0 的灯光会改变参与渲染的灯光数量，可能生成新的着色器变体；首次悬停时的编译卡顿可能抵消收益。

### 验证与建议

1. 按材质和透明类型统计实际 draw calls，确定哪些对象真正能合并。
2. 先尝试固定底座或同类不透明碑体；保留晶体、倒影和点击对象的独立行为。
3. 对比默认、四碑聚焦、快速切换、主题渐变和回程的 CPU/GPU 时间及截图。
4. 检查首次交互是否增加新程序编译、射线命中是否一致。

**建议：中等优先级，小范围试验；不一次性重写整个场景。**

## 2. 新叶喵不透明实体改为单遍绘制

### 原理与可能收益

- Three.js 对透明、双面 (DoubleSide) 材质通常先画背面再画正面，以改善透明遮挡；`forceSinglePass` 可以关闭该双遍策略。[官方材质说明](https://threejs.org/docs/pages/Material.html#forceSinglePass)
- 路卡材质已经根据实体不透明状态使用单遍。新叶喵从早期 chrome 材质克隆，后续路卡单遍开关不会自动更新克隆材质。
- 新叶喵完全不透明且深度测试/写入正确时，可能省掉实体的一次绘制。它不是“整个场景绘制成本减半”。

### 为什么不能只检查 `opacity === 1`

- 着色器还会叠加环境渐隐，材质 opacity 为 1 时，最终片元透明度仍可能小于 1。
- 聚焦时实体与线框混合，倒影本来就是半透明；这些阶段可能仍需要双遍。
- 切换单/双遍涉及着色器变体；若未预热，会把首次交互卡顿引入场景。

### 验证与建议

1. 记录默认/渐隐/线框/回程/倒影各阶段的实际材质状态与绘制调用。
2. 仅在有效透明度完全不透明时尝试单遍，并预热涉及的新变体。
3. 比较耳朵、尾巴、身体重叠处、背面与倒影，检查闪烁、穿透和透明顺序。

**建议：优先验证。改动范围较小，收益可通过实际少一次绘制直接核对；视觉通过后再实施。**

## 3. 分阶段着色器预热、返回首页复用 GPU 资源

### 两种不同的优化

| 方向 | 解决的问题 | 可能的代价 |
| --- | --- | --- |
| 分阶段预热 | 首屏一次准备大量程序/纹理，使首个可见画面出现较晚 | 未预热的阶段可能在首次点击时卡顿 |
| 复用 GPU 资源 | 离开首页再返回时重新建几何缓冲、纹理、程序和 WebGL 上下文 | 隐藏页面继续占用显存、上下文与资源管理容量 |

- 当前两轮 compile/render 对应不同裁切和透明渲染变体，有实际用途；不能把第二轮当作重复代码直接删除。
- `compileAsync` 利用并行着色器编译扩展，提前准备程序；它不等于消除所有纹理上传、缓冲初始化与首帧成本。[官方渲染器说明](https://threejs.org/docs/pages/WebGLRenderer.html#compileAsync)
- 模型 ArrayBuffer 已有会话缓存；GPU 缓存是另一个层级。首页内部切换模块也不会销毁首页场景，因此 GPU 复用主要影响真正离开路由再返回的行为。

### 验证与建议

1. 拆开记录下载、几何初始化、纹理上传、各轮编译、首次实际绘制与首次交互。
2. 区分首次冷进入、站内返回和反复访问；统计返回首页的频率，避免为少见路径保留大量 GPU 资源。
3. 若考虑缓存，先限制为一个首页场景，并设置过期和主动释放条件；继续暂停隐藏渲染。
4. 反复进出路由检查 GPU 资源、JS 堆、上下文丢失和移动端内存压力；处理配置变化与快速离场。

**建议：分阶段预热先测；GPU 缓存放在后面。它的维护与内存成本明显高于单遍材质优化。**

## 4. 高频指针合帧与命中轮廓投影简化

### 原理与可能收益

- 同一显示帧内可能收到多个原生指针事件；保留最新坐标、每帧集中分发，可能减少重复订阅回调和尾部 timer。
- 方尖碑点击区域由投影点、凸包排序和 DOM 盒/clip-path 表示。若运镜期间这些计算成为热点，可预计算固定拓扑、复用投影矩阵或减少命中层更新。

### 当前已经具备的优化

- 一个共享指针监听器，模型采样约 30Hz。
- 变形顶点拾取缓存；姿态未变时不再重复变形顶点。
- 点击轮廓只在构图变化时更新，样式相等不写入。
- 本轮进一步按变化更新世界矩阵与材质。

### 为什么仍需验证

- 新增帧调度可能增加等待，或在低帧率时降低跟手性。
- 直接用矩形替代投影凸包会使空白位置也可点击，改变实际交互。
- 当前几何规模有限；引入包围体层次结构 (BVH) 后，还需维护变形几何的加速结构，未必比现有线性拾取更便宜。

### 验证与建议

1. 在高采样鼠标持续移动、快速越过模型、运镜末帧等场景中，拆分事件分发、射线拾取、投影与 DOM 写入时间。
2. 比较输入到下一可见帧的延迟，以及停止移动后最后坐标是否正确送达。
3. 重跑多姿态、多缩放下的拾取一致性与键盘可访问性。

**建议：低优先级。没有新 trace 证明其占比明显之前，不加 BVH 或第二套指针调度系统。**

## 5. Typekit 按字体需求和入口状态调度

### 原理与可能收益

- 目前全站在 load 后通过 idle 回调调度 Typekit，超时为 1s；没有与 3D 入口就绪关联。
- 字体脚本解析、字体下载与字体替换可能和 3D 初始化争用主线程或网络。
- 如果某个路由首屏没有立即用到相关字体，可以按需求加载；如果确有资源争用，也可调整到入口关键阶段之后。

### 为什么不直接删除或统一延后

- `alibaba-puhuiti` 在全站广泛使用，不能认定 Typekit 无用。
- 延后可能让回退字体显示更久，之后替换导致行宽、高度和内容位置变化。
- 本次贡献图/矩阵隔离测量屏蔽 Typekit，因此这些数据不能证明 Typekit 的独立收益。

### 验证与建议

1. 开启真实 Typekit 请求，记录各字体的消费者、请求链、字体替换时刻和重排范围。
2. 分别测试正常、慢速、失败与热缓存，以及中英文路由。
3. 比较现有 idle、按字体需求、入口就绪后调度；同时衡量首屏速度、布局偏移和字体跳变。

**建议：保留当前字体效果，先测真实请求链。若只移动耗时而增加排版跳变，不采用该方案。**

## 6. 全局 CSS 与共享组件样式继续拆分

### 原理与可能收益

- 移动不属于首屏的组件样式到对应路由，可减少首屏 CSS 下载、解析和样式规则处理。
- 本次首屏 UI 分包已改变 CSS 依赖图；新构建首页实际请求 CSS 为 241,999 B，详见 [实施结果](./selected-optimization-results.md)，不能沿用旧的约 290KB 基线。
- 动画方案应通过实际布局/绘制分析判断；长期增加 will-change 不是通用解决方法。[Chrome 动画指南](https://web.dev/articles/animations-guide)

### 为什么未执行样式不能直接删除

- 首次加载没用到的规则可能属于菜单打开、浅色主题、英文、错误态、弹窗、离场或另一个断点。
- 动态 class、CSS 变量、scoped 样式和共享组件会使静态扫描漏掉合法消费者。
- 延迟加载真正需要的样式会出现无样式闪烁、尺寸跳变，甚至破坏路由离场几何和弹窗滚动。

### 验证与建议

1. 针对新生产构建绘制 CSS 依赖图与首屏阻塞链。
2. 在完整交互之后收集规则覆盖，覆盖桌面/移动、中英文、深浅主题、减少动效和弹窗。
3. 先按组件边界迁移路由专属样式，不先做全局粗暴删规则。
4. 比较下载/解析收益、首屏阻塞时间与视觉回归；离场及滚动偏移仍需 ≤1px。

**建议：中等优先级，跟随新构建数据决策；不依据“未执行比例”承诺等比例性能提升。**

## 推荐验证顺序

1. 新叶喵单遍绘制：改动与收益最容易隔离。
2. 分组统计绘制调用，尝试少量不透明几何合并。
3. 新构建 CSS 和真实 Typekit 请求链。
4. 首屏预热分阶段。
5. 高频指针与 GPU 场景缓存：只有新基线显示必要时再投入。

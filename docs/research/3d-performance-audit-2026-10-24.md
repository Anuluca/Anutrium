# Yuta Abe 与 Anutrium 3D 性能对比

审计日期：2026-10-24。范围：参考站首页猫模型、鼠标跟随、扫描与公开渲染管线；本地首页、首页 → Island 转场、Island 稳定跟随及相关 DOM、资源加载。结论来自公开 JavaScript、项目源码、实际 WebGL 调用记录、CPU 采样与 Chrome 性能轨迹，不是根据页面外观猜测。

## 1. 结论与测量边界

**参考站的优势主要是活动帧做的工作少：用定制着色器完成风格化效果、减少真实光照和重复表面绘制、让高成本后处理只在需要时运行。Anutrium 首页的主要改造空间是物理材质、倒影、透明叠绘和场景组织。Island 稳定态只有 3 次绘制，应另外处理扫描阶段、SVG/Vue 更新和外围动画。**

不能据此认定参考站所有方面都更好：Anutrium 已实现静止停绘、隐藏暂停、静态缓冲、鼠标共享采样与像素预算；这些应保留。

本次环境与限制：

- 视口 1440 × 900，DPR（Device Pixel Ratio，设备像素比）= 1；Chromium 149.0.7827.55。
- 自动化 Chromium 使用 **SwiftShader 软件渲染**，不是用户真实 GPU；GPU 计时扩展不可用。可以比较提交的绘制工作与代码结构，**不能据此发布真实显卡 FPS、GPU 毫秒、提升百分比或耗电百分比**。
- 本地是现有 Vite 开发服务，参考站是生产站。因此不比较两边开发/生产 JS 总体积，不把此次 LCP 当生产体验结论，也没有有效 INP 结论。
- 每个场景为一次采样，空闲约 4 秒、持续鼠标跟随约 5 秒。不是多设备统计结果。
- 审计期间工作区有其他修改：主基线的路卡为 1,527 面，后续关闭诊断的实验已变成 1,511 面；后者不用于因果性的性能提升结论。当前文件与测量版本可能存在行号偏移，证据文件记录了源文件指纹。
- 注入与临时关闭效果均只发生在独立测试浏览器内，没有改动业务源码或启动、停止开发服务。初始化入口留下的已失效 Canvas 不计为第二个活动 WebGL 上下文。

[完整测量摘要与场景快照](./3d-performance-audit-2026-10-24.evidence.json)。原始轨迹、CPU profile、截图、脚本及参考代码快照保存在 `/tmp/anutrium-perf-audit-20261024/`；临时目录可能被系统清理。

## 2. 实际工作量

表中“典型帧”是活动绘制帧的中位数。Draw call（绘制调用）统计来自底层 WebGL，不直接采用 Three.js 最后一次 `renderer.info.render.calls`：参考站一帧渲染多个 Scene，最后一个空场景会把该值重置为 0。

| 观察项 | 参考站首页 | Anutrium 首页 | Anutrium Island 稳定态 |
|---|---:|---:|---:|
| 持续跟随：绘制调用/典型帧 | 10 | 60，P95 为 62 | 3 |
| 三角形提交量/典型帧 | 2,698 | 9,739 | 3,511 |
| 另行提交的线段/典型帧 | 0，线框在片元着色器中生成 | 32 | 4,581 |
| 稳定空闲采样期间的 3D 绘制调用 | 530 | 0 | 0 |
| Three.js 已编译程序数 | 12 | 43 | 43，沿用首页资源 |
| 场景图中的不同材质对象 | 11 | 82 | 82，多数已隐藏 |
| 场景图中的真实 Three.js 光源 | 0 | 9 | 9，主要表面已改为 Basic |
| 跟随期间缓冲上传调用 | 360，胡须形变等 | 0 | 0 |
| 跟随期间新增程序链接 | 0 | 0 | 0 |

材质数不等于绘制数，也不等于程序数。隐藏对象仍占资源，但不一定提交绘制。三角形是各个 Pass 的提交总量，不能当成模型独立面数。Island 的 3,511 三角形包含 1,527 面的黑色表面与 1,984 面的立体标签，线框另计。

**首页约 6 倍的调用量不等于 6 倍耗时。** 材质复杂度、模型投影面积、透明叠绘、驱动和显卡都会改变结果。Island 在绘制调用数量上已经少于参考站。

### 对照实验

| 临时调整 | 基线 → 调整后 | 可以确认的结论 |
|---|---|---|
| 关闭首页倒影组 | 60 → 43 次/典型帧；9,739 → 4,227 三角形 | 当前倒影约占典型帧 28% 的调用和 57% 的三角形提交，值得优先改造 |
| Island 停止发布锚点 | 两边均为 3 次绘制 | 不影响 3D 工作量；可隔离 Vue/SVG 更新成本 |
| Island 锚点性能轨迹 | 基线 1,207 次 `line: SVG resource invalidated`；关闭后该项消失 | 逐帧 SVG 连线更新确实使浏览器执行额外工作 |
| 锚点实验总布局耗时 | 不同记录变化有限，且帧数、悬停切换不同 | 不足以证明锚点是主要瓶颈，不能宣称固定提速比例 |
| 关闭大块诊断发布 | 后续模型数据发生变化 | 仅确认可移除诊断路径，不用其总耗时作严格 A/B 结论 |

跟随轨迹还记录到光标 `.cursor-shape` 的 `Style changed` 布局失效，以及页脚 `.marquee-wrap` 的持续动画样式失效。性能轨迹事件存在嵌套，其耗时不可直接相加。

## 3. 参考站具体做了什么

公开入口：[网站](https://yutaabe.com/)、[模型与交互代码](https://yutaabe.com/_astro/index.DTZ4osvG.js)、[渲染 Stage 代码](https://yutaabe.com/_astro/stage.b6O6OWly.js)。这些是审计时的构建哈希，未来更新后链接可能失效。

### 3.1 材质与扫描：用定制计算替代通用渲染功能

- 猫身体与眼睛使用 `ShaderMaterial`，直接计算所需的漫反射、高光、边缘光、扫描和风格化线框；实际场景没有 Three.js Light。不会承担通用 Physical 材质的整套光照计算。
- 几何体转为非索引结构，增加重心坐标（Barycentric Coordinates）属性；片元着色器据此画三角形边缘。实体/线框/扫描通过同一表面的 uniform 混合，身体不需要为了每一种视觉模式完整重画一次。
- 扫描阈值、噪声和亮边在 GPU 内处理，跟随改变变换和 uniform，没有每帧重建几何或编译材质。
- 耳部形变放到顶点着色器。胡须仍有 CPU 更新，但隔帧执行，并复用已有向量和数组。

这不意味着参考站“完全零 CPU 几何更新”，也不意味着所有模型必须改成非索引。非索引方案会复制顶点，必须连同属性体积和缓存命中一起权衡。

### 3.2 跟随：输入轻、更新连续、阻尼按时间计算

- `pointermove` 主要保存归一化坐标，不在每次输入中测量 DOM 或对整个模型射线检测。
- `render()` 使用 delta time（帧间隔）计算阻尼；统一更新模型变换、鼠标平滑与材质 uniform。
- 它确实持续请求动画帧，并没有像本项目一样在稳定空闲后彻底停止 WebGL 绘制。该做法不是应直接照搬的节能优化。

### 3.3 后处理：分辨率受控，并且存在绕过路径

- 桌面 DPR 上限 2，移动端 1.5。
- 泛光（Bloom）缓冲长宽各为主目标的 0.5，像素量为 1/4；径向模糊移动端 8 次采样、桌面 16 次。
- 没有模糊、泛光等需求时走 `renderRaw()`，跳过整套后处理。触摸设备禁用部分径向模糊。
- 背景流体使用 CSS 尺寸的 0.75 倍长宽，不再乘设备 DPR，并有活动状态控制。
- Bloom 开启时仍需亮度提取、多个模糊通道和合成，不是免费效果。本项目当前主场景没有这套全屏后处理，不应为“优化”而额外加一套。

依据：[参考 Stage](https://yutaabe.com/_astro/stage.b6O6OWly.js)。

### 3.4 加载：按功能拆分

- 猫 GLB 使用 Draco；此次传输约 202 KB。背景 WebP 约 6 KB。
- F1、Projects、About、Playground 等功能有按需模块加载和 Promise 缓存；F1 模型不是首页猫跟随的必需开销。
- Astro 壳有利于把大量内容保留为静态 DOM，但猫的运行时效率主要来自渲染方案与工作量。没有证据支持把本项目改写为 Astro 就会解决跟随性能。

依据：[参考交互代码](https://yutaabe.com/_astro/index.DTZ4osvG.js)。Draco 改善传输，不会自动减少解码后每帧的绘制调用或片元开销。

### A1. 不要让每个小部件承担通用 Physical 材质

位置：`src/views/Home/templeScene.ts`，建筑 `surface/crystal`、主模型 `chromeMaterial` 和宠物实体材质。

当前建筑、晶体、模型、倒影包含 `MeshPhysicalMaterial`、clearcoat、环境采样、真实灯光，主模型还使用 ACES 色调映射。参考站采用针对视觉设计的简化光照。Three.js 官方明确说明 Physical 材质的每像素成本更高，具体取决于启用功能：[文档](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)。

建议按视觉重要性分级：

1. 路卡主表面保留当前效果作为对照，先把小建筑和倒影降为 Standard、Matcap 或定制高光/边缘光材质。
2. 若主模型仍是热点，再离线烘焙环境反射/Matcap，或用少量方向参数实现风格化金属。保留主题染色、转头和扫描 uniform 接口。
3. 单独测“无 clearcoat”“简化倒影材质”“简化建筑材质”，避免一次全改后无法判断收益。

风险：Matcap 会改变物体移动时反射的物理关系；不能承诺视觉完全无差异。当前环境数据已经离线烘焙，不应再把“移除运行时 PMREM 生成”列作收益。

### A2. 倒影不要照搬所有实体材质

位置：`mirror()`，约 923 行起。它复用几何，但克隆并透明化材质，仍再次渲染相应表面。当前没有额外离屏模糊 Pass，这是已有优点。

改造从低到高：

- 保留镜像几何，先将倒影转成统一的便宜着色器，减少真实光照、clearcoat 与独立材质。
- 静态建筑倒影合批；动态路卡/宠物倒影独立。
- 若镜头和建筑通常静止，将静态倒影缓存到较小的渲染目标，只在相机、布局、主题、灯光或建筑状态变化时重画。动态头部另绘。

对照实验已经给出工作量上限：完全去掉倒影可少约 17 次调用、5,512 个三角形提交；保留视觉的优化只能收回其中一部分。缓存会增加纹理/合成及失效管理，不能保证一定比镜像几何更快，必须在真实移动 GPU 上验证。

### A3. 大改方案：把“所有物体在一个 Scene 里重绘”改为分层渲染

持续转头会让首页整个可见场景重画。矩阵冻结只能减少 CPU 矩阵工作，不能免除静态建筑的 GPU 绘制。

建议创建一个渲染宿主，分成静态环境、动态角色、动态倒影、屏幕装饰四部分。静态层在相机/主题/建筑/光照变化时重绘，角色转头只绘动态部分。入场和运镜期间允许全量更新，稳定后切回缓存。

必须处理：静态层与动态角色的深度遮挡、透明地面、抗锯齿目标、色调映射只执行一次、悬停变暗的失效条件、DOM 卡片与 Canvas 的现有层级。不能简单截图成背景后忽略遮挡。

这是比继续压缩路卡几十个面更值得做的重构候选。建议先做单独实验开关，再按硬件 GPU 时间决定是否采用；不预先承诺调用数目标或 FPS 倍数。

### A4. 反复出现的四柱适合批处理

四根柱共享大量结构，但为每根柱、每个倒影创建单独材质。将类别颜色、悬停强度、透明度等变为实例属性/uniform 数据，按材质合批。

- 相同几何/材质使用实例化（InstancedMesh）。
- 不同几何但同材质可评估 BatchedMesh；透明排序、扩展支持与实际批次收益需要检查。
- 小量固定静态子件可直接合并 BufferGeometry。本项目部分底座已合并，不是从零开始。
- 边线、光池、标签按用途分别批处理，不把所有物体硬塞进一个巨大 Mesh。

参考：[InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)、[BatchedMesh](https://threejs.org/docs/pages/BatchedMesh.html)。保持实例级点击身份；镜头运动、柱子伸缩和悬停颜色必须有对应的数据更新机制。

### A5. 零亮度灯仍占光照槽位

运行时首页有 5 个 `visible=true`、`intensity=0` 的 SpotLight。已编译程序中，19 个程序具有长度为 5 的 `spotLights` uniform 序列。所用 Three.js 的 `projectObject()` 会收集可见 Light，`WebGLLights` 不因亮度为 0 自动排除它。

建议把“多个常驻光源”改成少量可复用灯，或在专用材质中用局部参数计算效果。若某状态仅需要一个聚光灯，就不要在着色器里保留五个。

不要在每帧随亮度随意切换 `visible`：光源数量变化可能产生新程序变体和卡顿。应使用有限状态/固定光源池并预热需要的变体。Island 的 Basic 表面不执行 PBR 光照，不能把这里的收益套到 Island 稳定态。

### A6. 扫描四表面值得合并，但不是所有层都可无条件合成一层

当前主体由 chrome、wireframe、半透明黑色填充、加色扫描光晕组成；扫描进行时四表面可能同时绘制，头部形变与分界计算也重复执行。稳定 Island 只有黑色面与线框，再加标签共 3 次调用。

优先尝试将黑色填充、线框、扫描亮边合进同一个定制着色器。再评估是否连 chrome 也纳入单一材质。重心坐标线框可获得可控线宽和抗锯齿，但会增加顶点属性/非索引数据。

特别约束：当前黑色面透明度 0.55，同时写深度，目的是压暗背后卡片并遮住背面线框。单材质方案必须保留该语义，必要时仍用深度预通道（Depth Prepass）。发光外扩轮廓若不能在表面 Pass 保留，也可留下独立窄光晕 Pass。目标是减少重复工作，不能为了单次调用破坏遮挡和半透明效果。

### A7. 透明、双面与重复覆盖

- 主 chrome 配置 `transparent:true`，稳定时 opacity=1；建筑材质因入场动画会被设置透明。
- 晶体为双面透明、clearcoat=1，镜像又重复相应绘制。双面透明默认可能需要前后两遍；主 chrome 已设 `forceSinglePass=true`，不应再把它当作未做优化。
- 检查稳定不透明对象能否回到不透明队列；晶体是否确需双面、两遍排序和所有内芯叠层；倒影是否可使用更简单规则。
- 前后裁切面、光池和发光面应尽量缩小包围区域；opacity=0 且没有深度用途时应隐藏，而非只靠透明度。

状态切换与变体应预热，透明排序和穿透效果需逐一视觉回归。不能全局设置 `forceSinglePass` 或关闭透明。

### B1. 预热要保留，但可以更有针对性

`prepareRendering()` 在开放交互前编译并实际绘制多个变体；这是避免第一次扫描卡顿的正确方向。本次预热后有 43 个程序，跟随期间无新链接。

改造：按入口只准备首帧所需的少量材质；下一步高概率交互用空闲任务预热；降低材质/光源变体本身的数量；避免给永远不展示的组合预热。要同时记录“首个可见模型时间”和“首次交互是否编译”，不能把卡顿从加载阶段挪到点击阶段。

### B2. 让锚点运动不触发静态卡片组件更新

链路：`templeScene.ts` 投影五个点 → `TemplePage.vue` 比较 0.25px 阈值并替换 `shallowRef` → `IslandFocusLayout.vue` 重建 links 数组/排序并更新 SVG。

建议 Vue 只负责静态内容、布局与悬停状态；模型帧直接更新持久化线段/端点节点。先做最小范围的命令式 SVG 更新；若 Paint 仍明显，再考虑独立 Canvas 或同一 WebGL 宿主的正交线层。

命令式 SVG 只能省 Vue diff，**不会让 SVG 自身重绘消失**；Canvas/WebGL 方案才可能进一步减少布局失效，但会增加渲染/缩放处理。端点实际移动超过阈值时才写入，数据对象与排序结果复用。ResizeObserver 目前主要用于布局、字体、语言和尺寸变化，没有证据表明它每次跟随都读取布局，不应误判。

### B3. 光标位置已优化，形状动画仍触发布局

`CursorMove/index.vue` 约 438 行：hover 时 width、height、margin 做 1 秒过渡。跟随穿过不同交互区会多次触发这些布局动画；轨迹已确认 `.cursor-shape` 的布局失效。

改为固定 36px 的包围盒，圆形/三角形独立子层，用 transform 和 opacity 变化；保留现有静止停 RAF。`mix-blend-mode:difference`、drop-shadow、clip-path 叠加的合成成本须另做视觉/硬件验证，不能只因存在 filter 就断言慢。此项不要把“去掉光标效果”当唯一方案。

### B4. 诊断发布从运行路径移出

`publishDiagnostics` 涉及大量 `toFixed/map/join`、颜色字符串、额外投影与 dataset 发布。已有 100ms 限频和相同值不写入的缓存，但 `diagnosticsDirty` 为真会绕过间隔；扫描/缩放 onUpdate 会逐帧置脏。部分诊断调用还在大块发布逻辑之外。

使用显式构建/测试参数启用诊断，把必须保留的产品状态属性单独维护；测试通过开关读取相同数据。仅移除 `dataset` 写入不足以省掉前面的格式化/投影。此项属于低成本清理，没有证据证明它能单独解决明显掉帧。

### B5. 固定像素上限之外，增加质量控制

当前 DPR 1.5 / 约 419 万像素已经比参考站桌面上限更克制。但不同设备的算力差异远大于尺寸差异。

可按设备实测帧耗时/GPU 计时做动态分辨率（Dynamic Resolution Scaling），例如有限档位切换，并配合倒影质量、光照复杂度、光晕等级；持续压力降档，稳定一段时间才升档。不能把 RAF 间隔直接当 GPU 时间，也要排除切后台、网络解码和主动停绘。

降低 DPR 到原来的 0.8，像素量理论上变为 0.64；这不是总耗时或 FPS 的固定收益。清晰度、切档抖动和重分配代价都需要验证。

### B6. 持久宿主与按状态加载

当前会话 Promise 缓存避免重复下载，但 Scene 每次创建仍重新分配 GPU 资源、材质和程序；卸载时释放。首页与 Island 之间已经可以共享场景，不应误称它们每次都重建。

可将 WebGLRenderer/关键角色资源放到 App 级宿主，路由只切场景状态；其它页面暂停该宿主，超时/内存压力再释放。资源池要有引用计数和上限，不能永久保存所有路由的模型与纹理。结合 A3，可将大文件拆成 RendererHost、TempleEnvironment、Character、ScanMaterial、AnchorOverlay、TransitionController 等职责。

## 6. 次级机会与边界

### C1. DOM 与 Canvas 的合成面积

Island 背景封面有 SVG 色彩滤镜，标题有镂空/渐隐，连线覆盖视口；光标使用差值混合和投影。先缩小动态绘制范围、隔离静态层，再逐项关闭 filter/blend 做硬件轨迹。不要给所有元素加 `will-change` 或 `translateZ(0)`，它们会增加合成图层与内存。

### C2. 统一动画状态，不盲目统一成一个永远运行的 RAF

本次首页空闲虽然 3D 不画，约 4 秒仍有 639 次样式重算；轨迹确认页脚 marquee 持续活动。该动画已经使用 translate3d 且支持隐藏页面/减少动态时暂停。当前软件合成环境可能放大它的成本，必须用真实合成轨迹复核。

粒子首页已限 12 FPS，桌面数量约 130、移动端约 33。可在转场繁忙或完全被覆盖时暂缓粒子和页脚动画；需要持续视觉时降低背景更新频率。统一调度的价值是避免无效唤醒与错序读写，不能牺牲已有各模块停绘机制。

### C3. 样式依赖与覆盖层

轨迹出现 `Affected by :has()` 的 `.temple-page` 祖先失效。`TemplePage.less` 用后代状态控制整页遮罩；可改为页面已知状态 class，使悬停/后代变化不必影响大范围祖先选择器。先按轨迹定位实际选择器，不全局禁用 :has。

Island 为了卡片在模型后、交互在模型前保留两层 DOM；重构时可将交互数据和视觉数据共享，减少不必要组件更新，但不能破坏点击和屏幕阅读器语义。

### C4. 字体影响加载与首段动画

此次首页加载观察到 Typekit 字体数据/增量字形 8 次请求，传输合计 1,850,591 字节，约 1.76 MiB。该资源量明显超过约 38 KB 的路卡几何。CPU 采样中也出现 Typekit 脚本和 FontFace 工作。

当前已有 idle 调度，Unbounded 也有分片/preload；不要建议简单“再延迟一次”。应核对首页实际使用的 Typekit 字重与字符范围，按路由/字形需求加载，避免当前首屏不需要的多字重同时参与首段动画。是否可进一步自托管取决于字体许可，不能默认可复制 Adobe 字体。此项主要改善加载与字体切换，不是稳定 3D GPU 优化。

### C5. 模型包已经很小，入口资源仍可拆

基线传输：路卡几何约 37,956 B；宠物约 48,632 B；标签约 34,049 B；预烘焙环境约 492,394 B。环境为 384×512 的半浮点 CubeUV 数据，解压约 1.5 MiB，规模并不异常。

直接进入纯 Island 时，可只准备线框/黑色面和标签，把 chrome 环境与首页宠物推迟到需要恢复首页之前。该方案依赖 B1/B6 的状态化初始化，不能破坏返回首页扫描的无缝材质恢复。缓存头只能在生产部署验证；Vite 的 no-cache 不是线上缓存故障证据。

参考站 GLB 使用 Draco，不代表本项目也该添加 Draco：当前几何已经小于参考站 GLB，增加解码器可能得不偿失。若以后模型或纹理显著增长，再评估 meshopt/KTX2。

### C6. 最后再清理小对象与数学计算

五个锚点每帧创建新对象、links flatMap/map/sort、诊断格式化、重复头部变换均可复用；把热点变成预分配 Float32Array/Vector 和变化标记。当前只有五个锚点，收益小于改材质与倒影。不要为了减少几个对象引入难维护的对象池体系。

### C7. 立体标签可以分质量等级

Island 标签 1,984 面略多于模型黑色面的 1,527 面，但总量仍小。它已离线生成，不存在运行时字体挤出问题。低端设备可试平面纹理/SDF 或更少侧面细分；保留高质量立体版本。它不是当前首要的面数瓶颈。

## 7. 不建议作为第一步的“大改”

| 方案 | 判断 |
|---|---|
| 全站从 Vue 改 Astro/React | 无证据支持；只有高频锚点路径需要脱离组件重渲染 |
| 整站改 WebGPU | 先减少无效绘制与材质复杂度；换 API 不会自动消除它们，兼容与回归成本高 |
| 立即迁移 Worker + OffscreenCanvas | 有大量主线程阻塞证据时再做；不能减少同样的 GPU 片元工作，还需解决 DOM 锚点与事件通信 |
| 继续大幅压缩路卡面数 | 当前约 1.5K 面，优先级明显低于倒影/PBR/重复 Pass；会先损伤轮廓 |
| 无条件加 BVH | 当前模型小且已有输入限频、命中对象筛选；没有足够的射线检测热点证据 |
| 去掉所有预热 | 可能让首次扫描/点击新增编译卡顿，应分层预热而非删除 |
| 所有静态内容都截图 | 会破坏运镜、遮挡与交互变暗；必须有正确的分层与缓存失效 |
| 全局提高 DPR、强制高性能 GPU、堆 will-change | 可能更耗电或占更多内存，不是已经验证的性能修复 |

## 8. 建议实施与验收顺序

1. **低风险清理**：诊断开关、光标固定盒子、锚点更新隔离。保留现有视觉、停绘与测试语义。
2. **首页渲染减负**：先做可切换的倒影简化、建筑材质降级、光源池和透明层整理，逐项硬件 A/B；再做实例化/合批。
3. **扫描专项**：定制统一表面与重心坐标线框原型，先验收黑色半透明深度遮挡、扫描边缘、转头与返回效果，再比较 GPU 时间。
4. **架构专项**：静态/动态分层、持久 RendererHost、按入口预热与资源准备、质量等级。

真实硬件验收至少覆盖：桌面集显/核显、Mac 浏览器、iPhone Safari，以及一个较弱移动设备；生产构建、相同视口/像素预算、固定相同鼠标轨迹，采样多轮。

记录：活动帧间隔 P50/P95/P99、掉帧分布、主线程任务、可用时 GPU 时间、绘制/程序/上传计数、峰值资源和连续路由往返后的资源释放。60Hz 完整帧预算为约 16.7ms，渲染不能独占全部预算；高刷屏需要另行确定目标。

现有 `tests/island-performance.spec.ts` 应保留，并补充分状态绘制预算、首次扫描零编译、静止和隐藏零绘制、路由往返资源上限。实现涉及全屏/路由过渡时还必须执行项目要求的桌面/移动端离场几何回归。此次只做审计，没有运行与改动无关的全量测试。

性能验证方法参考：[Chrome Performance](https://developer.chrome.com/docs/devtools/performance/reference)、[MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)。以上优化项的收益仍须逐项实机验证，不能把实验中的调用减少直接换算成帧率提升。
